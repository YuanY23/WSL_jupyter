## 1. 项目定位

本项目是一个基于 Jupyter 生态的教学仿真一体化平台。它不是单一前端应用，也不是单纯的 JupyterHub 部署脚本，而是把 `JupyterHub`、`DockerSpawner`、`JupyterLab`、`nbgrader`、Python 科学计算库和三套自研 JupyterLab 扩展组合在一起，形成“多用户教学管理 + 多课程作业评分 + 白箱式仿真实验 + Notebook 参数交互”的完整系统。

项目核心目标可以概括为四点：

1. 通过 JupyterHub 管理用户登录、注册、角色、课程分组、RBAC 权限和容器生命周期。
2. 通过 DockerSpawner 为每个用户启动隔离的一致化 JupyterLab/nbgrader/Python 环境。
3. 通过 nbgrader 支撑教师发布作业、学生获取与提交、教师收集、自动评分、人工评分和反馈发布。
4. 通过自研 JupyterLab 扩展生成可阅读、可运行、可修改、可归档的白箱式仿真 Notebook，并进一步提供参数侧边栏交互。

与旧版总结相比，当前 v2 需要特别更新以下事实：

1. 参数绑定能力已经从 `jupyterlab-thermal-design` 中拆出，成为独立扩展 `jupyterlab-param-binding`。
2. 旧版文档中的 `# @param` 注释方案已经不是当前实现主线；当前实现基于 Markdown 标题“参数层代码”区域扫描和 Notebook 顶层 `simulation_param_bindings` 元数据。
3. 热设计插件菜单与标题已统一为“传热仿真平台”，通用模板扩展统一为“通用仿真平台”。
4. 热设计生成的 Notebook 与通用模板生成的 Notebook 当前统一保存到 `simulation-platform-results/`。
5. Docker 构建已经加入参数绑定扩展、默认拒绝式 `.dockerignore`、扩展依赖预安装层和开发态源码挂载。
6. 通用仿真模板新增参数控件配置字段、参数绑定元数据生成、文件名清理和更完整的生成器测试。

## 5. JupyterHub 管控层

### 5.1 自定义认证与注册

`jupyterhub_config.py` 设置：

```python
c.JupyterHub.authenticator_class = CustomNativeAuthenticator
```

`custom_authenticator.py` 中的 `CustomNativeAuthenticator` 继承 `NativeAuthenticator`，并通过 `get_handlers()` 替换默认 `/signup` handler。注册页增加两个业务字段：

| 字段 | 说明 |
| --- | --- |
| `role` | `student` 或 `teacher`。 |
| `course_id` | 课程 ID，教师必填，学生选填。 |

注册时的后端处理流程：

1. `CustomSignUpHandler.post()` 读取用户名、密码、邮箱、2FA、`role`、`course_id`。
2. 校验密码确认、用户名占用和 reCAPTCHA 状态。
3. 调用 `self.authenticator.create_user(role=role, course_id=course_id, **user_info)`。
4. `CustomNativeAuthenticator.create_user()` 先调用父类创建 NativeAuthenticator 用户。
5. 再通过 JupyterHub ORM 查找或创建 Hub 用户和 group。
6. 根据角色和课程写入 group。

当前 group 命名规则：

| Group | 语义 | 写入时机 |
| --- | --- | --- |
| `teachers` | 全局教师组 | 教师注册成功后。 |
| `formgrade-{course_id}` | 某课程教师组 | 教师注册并填写课程 ID 后。 |
| `nbgrader-{course_id}` | 某课程学生组 | 学生注册并填写课程 ID 后，或教师在 Formgrader 添加学生时。 |

这个 group 模型是平台最重要的统一事实来源。它同时驱动容器挂载、nbgrader 课程可见性、教师权限、学生作业列表和课程目录隔离。

### 5.3 DockerSpawner 与教师动态注入

基础 Spawner 配置：

```python
c.JupyterHub.spawner_class = dockerspawner.DockerSpawner
c.DockerSpawner.image = 'my_jupyterhub:latest'
c.DockerSpawner.default_url = '/lab'
c.DockerSpawner.notebook_dir = '/home/jovyan'
```

所有用户基础卷：

| 宿主机或 Docker 卷 | 容器内路径 | 作用 |
| --- | --- | --- |
| `jupyterhub-user-{username}` | `/home/jovyan` | 用户家目录持久化。 |
| `/srv/nbgrader/exchange` | `/srv/nbgrader/exchange` | nbgrader 作业交换目录。 |
| `/home/yuan/my_project/nbgrader` | `/src/nbgrader` | nbgrader 源码开发挂载。 |
| `/home/yuan/my_project/jupyterlab` | `/opt/jupyterlab` | JupyterLab 源码开发挂载。 |
| `/home/yuan/my_project/jupyterlab-param-binding` | `/src/jupyterlab-param-binding` | 参数绑定扩展源码挂载。 |
| `/home/yuan/my_project/jupyterlab-simulation-platform` | `/src/jupyterlab-simulation-platform` | 通用仿真平台源码挂载。 |
| `/home/yuan/my_project/jupyterlab-thermal-design` | `/src/jupyterlab-thermal-design` | 传热仿真平台源码挂载。 |
| `*-node-modules` Docker 卷 | 对应扩展 `node_modules` | 避免宿主机依赖目录污染，同时让容器内依赖持久化。 |

教师容器启动时，`pre_spawn_hook(spawner)` 会读取用户 groups。如果发现 `formgrade-{course_id}`：

1. 创建宿主机课程目录 `/home/yuan/my_project/courses/{course_id}`。
2. 设置目录 owner 为容器内 `jovyan` 的 UID/GID。
3. 挂载到容器内 `/home/jovyan/{course_id}`。
4. 注入 `NBGRADER_COURSE_ID={course_id}`。
5. 注入 `NBGRADER_ADMIN_API_TOKEN`，供 nbgrader 管理 Hub group。

学生容器没有 `NBGRADER_COURSE_ID`，不会获得教师课程目录，也不会获得管理 token。

### 5.4 RBAC 权限

`c.JupyterHub.load_roles` 定义 `formgrade-teacher` 角色，把以下 scopes 授予 `teachers` 组：

```text
list:users
read:users
read:groups
list:groups
admin:groups
access:services
```

达成效果：

1. 教师能读取用户和 group，用于 Formgrader 学生管理。
2. 教师容器通过注入的服务 token 能访问 Hub API。
3. nbgrader 可以把学生加入 `nbgrader-{course_id}` group，实现教师端学生管理和学生端课程可见性的同步。

### 6.2 构建层优化

当前 Dockerfile 有一个重要工程改进：先复制自研扩展的稳定元数据和 Python 包入口，预安装依赖，再复制完整源码。

流程示例：

1. 复制 `jupyterlab-thermal-design/setup.py`、`package.json`、`yarn.lock`、`.yarnrc.yml`、Python 包入口和 `thermal_solver`。
2. `pip install -e .`。

4. 对 `jupyterlab-simulation-platform` 和 `jupyterlab-param-binding` 做同样操作。
5. 后续再复制完整源码并构建。

当前主流程仍以“前端生成自包含 Notebook”为主，`thermal_solver` 更像算法库基础，可用于后续 Kernel 直接调用、后端 API 化或批量计算。

## 11. 自研扩展三：`jupyterlab-param-binding`

### 11.1 模块定位

`jupyterlab-param-binding` 是当前新增的独立参数自动绑定扩展。它提供一个 JupyterLab 左侧栏 widget，自动扫描当前 Notebook 中“参数层代码”区域的普通 Python 赋值语句，并根据 Notebook metadata 或自动推断生成控件。

它解决的问题是：

1. Notebook 保留完整代码，学生仍能读懂和修改。
2. 学生不必每次手工改代码和逐个运行单元格。
3. 教师生成的 Notebook 可以附带控件配置，形成可交互实验。
4. 参数交互能力不再只服务传热插件，而可服务任何带“参数层代码”的 Notebook。

### 11.2 插件入口

`src/index.ts` 注册：

| 项 | 值 |
| --- | --- |
| 插件 ID | `jupyterlab-param-binding:plugin` |
| 左侧栏 widget ID | `jupyterlab-param-binding:sidebar` |
| 标题 caption | 参数自动绑定 |
| 依赖 | `INotebookTracker` |
| 图标 | 自定义 sliders SVG `LabIcon` |

### 11.3 扫描规则

核心常量：

```typescript
export const BINDING_METADATA_KEY = 'simulation_param_bindings';
export const PARAMETER_REGION_TITLE = '参数层代码';
```

`scanParameterRegion(cells, metadata)` 的逻辑：

1. 遍历 Notebook cells。
2. 遇到 Markdown heading 时解析标题等级和标题文本。
3. 标题包含“参数层代码”时进入 active region。
4. 遇到同级或更高级 Markdown heading 时退出 active region。
5. 只扫描 active region 内的 code cell。
6. 只识别普通 Python 赋值：

```python
变量名 = 字面量
```

支持的字面量：

1. 数字：整数、小数、科学计数法。
2. 布尔：`True`、`False`。
3. 字符串：单引号或双引号。

不会识别 `np.array(...)` 等复杂表达式为单个参数控件，这降低了误判概率。

### 11.4 元数据与默认推断

如果 Notebook 顶层 metadata 中有：

```json
{
  "simulation_param_bindings": {
    "version": 1,
    "title": "参数层代码",
    "parameters": {
      "k": {
        "type": "slider",
        "label": "导热系数",
        "min": 0.01,
        "max": 5000,
        "step": 0.1,
        "group": "参数层代码"
      }
    }
  }
}
```

扩展会优先使用 metadata。没有 metadata 时会自动推断：

| 参数类型 | 默认控件 |
| --- | --- |
| `boolean` | 开关 |
| `string` | 文本输入 |
| `number` | 数字输入，必要时可配置为 slider |

数值控件会自动处理：

1. `min`、`max` 缺省推断。
2. `step` 缺省推断。
3. `max <= min` 时自动修正。
4. 范围步数超过 10000 时自动增大 step。
5. 当前值超出范围时 clamp range 值，但保留输入框值。

### 11.5 侧边栏交互

`ParamSidebar.tsx` 提供：

1. 刷新扫描按钮。
2. 运行下游按钮。
3. 自动计算下游开关。
4. Kernel 状态提示。
5. 分组折叠。
6. 参数控件。
7. 参数设置 details 面板。

支持控件：

| 控件类型 | UI |
| --- | --- |
| `slider` | range 滑块 + number 输入框 |
| `number` | number 输入框 |
| `boolean` | switch 开关 |
| `dropdown` | select |
| `text` | 文本输入 |

参数配置面板支持修改：

1. 显示名。
2. 控件类型。
3. 最小值。
4. 最大值。
5. 步长。
6. 下拉选项。

配置会通过 `updateNotebookBindingConfig()` 写回 Notebook metadata，因此 Notebook 可以携带自己的交互配置。

### 11.6 代码回写与运行

用户修改参数后：

1. `updateNotebookParamValue()` 定位目标 cell。
2. `updateAssignmentSource()` 替换对应行右侧字面量。
3. 使用 `cell.model.sharedModel.setSource(updated)` 写回 Notebook。
4. 如果开启自动运行，调用 `runCellAndDownstream()`。
5. `runCellAndDownstream()` 从参数区域起始 cell 开始，使用 `NotebookActions.runCells()` 运行后续所有单元格。

重要点：

1. 当前实现不会向源码插入 `@param` 注释。
2. 字符串会保留原来的引号风格。
3. 布尔值会写成 Python 的 `True` / `False`。
4. `isSyncingRef` 用于避免侧边栏更新和 Notebook 执行事件循环触发。

### 11.7 参数绑定测试

`jupyterlab-param-binding/tests/param-binding.test.js` 覆盖：

1. 扫描“参数层代码”区域内普通赋值。
2. 不扫描离开参数层后的变量。
3. 数字、布尔、字符串识别。
4. 更新普通赋值时不添加 `@param` 注释。
5. metadata 配置清理 undefined 字段。
6. 异常 min/max/step 自动修正。
7. 大范围 slider 步数上限控制。
8. 极小数值步长稳定性。
9. 配置 details 面板保存后不会强制关闭。

### 13.2 从 `# @param` 演进为 metadata/参数层区域

```python
k = 5.0  # @param {...}
```

当前实现不要求这种注释，而是：

1. Markdown 标题包含“参数层代码”。
2. 后续 code cell 写普通赋值。
3. Notebook 顶层 metadata 提供控件配置。
4. 没有 metadata 时自动推断控件。

技术效果：

1. Notebook 代码更接近普通 Python 教学代码。
2. 控件配置不污染代码行。
3. 参数绑定扩展可以服务由不同生成器生成的 Notebook。

## 15. 风险、限制与后续注意点

### 15.1 当前配置偏开发/测试

当前 JupyterHub 配置中：

```python
c.CustomNativeAuthenticator.open_signup = True
c.CustomNativeAuthenticator.minimum_password_length = 1
c.Authenticator.allow_all = True
```

这些适合本地测试，不适合生产部署。正式部署应提高密码强度、关闭开放注册或增加审批/外部身份源，并审查管理员用户和 token 生命周期。

### 15.2 路径硬编码

多个配置使用 `/home/yuan/my_project`、`/srv/nbgrader/exchange`、`172.17.0.1` 等固定路径或地址。迁移部署前需要参数化或改为环境变量。

### 15.3 CSP 设置宽松

Dockerfile 中设置了：

```json
"Content-Security-Policy": "frame-ancestors 'self' * *"
```

这对开发和嵌入方便，但正式部署应收紧。

### 15.4 端到端测试仍不足

当前测试主要覆盖纯生成器和解析逻辑，尚缺：

1. JupyterHub 注册流程端到端测试。
2. 教师/学生容器启动差异测试。
3. nbgrader 作业发布、获取、提交、收集完整流程测试。
4. 参数侧边栏真实浏览器交互测试。
5. Docker 镜像构建和启动冒烟测试。

### 15.5 `thermal_solver` 与 Notebook 生成主链路仍分离

`thermal_solver` 已经沉淀了求解器库，但当前用户主流程主要生成自包含 Notebook。后续如果要做实时后端计算、批量仿真或 API 服务，需要进一步设计 Kernel/Server API 和结果协议。

### 15.6 旧设计文档已过期

`docs/superpowers/specs/2026-05-21-bidirectional-binding-design.md` 记录的是旧 `# @param` 注释方案。当前代码已经实现 metadata/参数层扫描方案。后续文档应以本 v2 和当前源码为准。

## 16. 总结

当前项目已经形成一个较完整的教学仿真平台原型：

1. 平台层面，JupyterHub + DockerSpawner 负责多用户、多角色、容器隔离和环境一致性。
2. 教学层面，nbgrader 与 JupyterHub group 集成，形成多课程作业发布、提交、评分和反馈闭环。
3. 仿真层面，传热仿真平台覆盖 14 个专业传热场景，通用仿真平台覆盖 7 类教学建模模板。
4. 交互层面，独立参数绑定扩展把生成 Notebook 从静态白箱文档推进到可调参、可自动运行的交互实验。
5. 工程层面，Docker 构建、源码挂载、`.dockerignore`、测试文件和中文门户已经支撑本地开发与演示。

v2 的关键结论是：项目已经从“白箱 Notebook 生成器 + 教学管理平台”进一步演进为“可交互的 Notebook 仿真实验平台”。新增的 `jupyterlab-param-binding`、参数绑定 metadata、参数控件配置、统一输出目录和构建链路优化，是当前版本最重要的新功能和新技术。
