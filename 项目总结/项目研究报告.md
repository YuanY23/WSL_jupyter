# 基于 Jupyter 生态的白箱式热力仿真与教学管理平台设计与实现

## 摘要

随着工程教育、实验教学和科研训练不断向数字化、在线化和可复现实验方向发展，传统课堂中依赖纸质作业、单机仿真软件和人工收发文件的教学方式已经难以满足复杂工程问题的学习需求。尤其在热力学、传热学、能源系统分析等课程中，学生不仅需要得到仿真结果，更需要理解物理模型如何被抽象为数学方程，数学方程如何被离散为计算程序，程序运行后又如何产生图表、指标和工程判断。传统仿真软件虽然能够提供较为成熟的图形界面，但其计算过程通常被封装在内部，学生面对的往往只是参数输入框和结果输出图，难以深入理解模型假设、控制方程、数值求解和误差来源。

本项目围绕“显示计算代码的热力仿真系统”这一主题，构建了一套基于 Jupyter 生态的教学仿真一体化平台。系统以 JupyterHub 作为多用户入口和管控中心，以 DockerSpawner 实现用户运行环境隔离，以 JupyterLab 作为浏览器端交互式开发与学习环境，以 nbgrader 实现课程作业发布、提交、收集、自动评分和反馈闭环，并在此基础上开发热设计原理仿真插件和通用仿真模板生成器。平台的核心思想不是把仿真过程封装成黑箱按钮，而是自动生成可阅读、可运行、可修改、可保存的 Jupyter Notebook，使学生能够沿着“物理对象、数学模型、计算代码、可视化结果、分析结论”的路径完成学习。

项目在系统层面实现了教师和学生角色的注册、分组、课程绑定和权限控制；在课程层面实现了多课程目录管理和 nbgrader 作业流转；在仿真层面实现了热传导、对流换热、热辐射等典型热物理场景的参数化建模与 Notebook 生成；在交互层面进一步实现了基于 `# @param` 注释的 Notebook 参数自动识别、侧边栏控件生成、代码反向更新和下游单元格自动运行。由此形成了一个兼具教学管理、实验仿真、代码可见性和交互式学习能力的综合平台。

关键词：JupyterHub；JupyterLab；nbgrader；热力仿真；白箱式仿真；Notebook 自动生成；工程教育；Docker

## 第一章 绪论

### 1.1 研究背景

工程类课程的学习过程具有明显的“理论、计算、实验、评价”一体化特征。以传热学和热设计课程为例，学生需要理解导热、对流和辐射三类基本换热机制，需要掌握稳态与瞬态传热问题的数学建模方法，还需要能够通过数值计算得到温度场、热流密度、换热系数、系统效率等工程指标。传统课堂通常以板书推导、课后习题和实验报告为主，学生对公式推导有一定接触，但对“公式如何变成可执行程序”这一环节接触不足。另一方面，常见商业仿真工具虽然操作直观、功能丰富，但大多采用黑箱式交互方式，学生难以看到内部计算代码，更难以在同一环境中完成模型修改、参数扫描和结果解释。

Jupyter Notebook 的出现为工程教育提供了一种新的载体。Notebook 可以把 Markdown 说明、数学公式、Python 代码、运行结果和可视化图表组织在同一个文档中，天然适合教学演示、实验报告、课程作业和科研记录。JupyterLab 则在 Notebook 基础上提供了更完整的浏览器端工作环境，支持文件管理、终端、扩展插件、命令系统和多文档工作流。JupyterHub 进一步解决了多用户访问和统一管理问题，使同一套 Jupyter 环境能够服务于一个班级、一门课程甚至多个课程。

本项目正是在这样的背景下产生的。项目希望把 Jupyter 生态中的多用户管理、交互式 Notebook、作业评分和自研仿真工具整合起来，形成一个面向课程教学和科研训练的统一平台。它并不只是给学生提供一个在线 Python 环境，也不只是把 nbgrader 部署起来收作业，而是试图构建一个能够贯通课程组织、实验仿真、代码展示和作业评价的综合系统。

### 1.2 问题提出

在现有教学实践中，至少存在四类问题。第一，仿真过程与教学过程相互分离。学生可能在一个软件中做仿真，在另一个系统中提交作业，再通过邮件、网盘或纸质材料接收反馈。工具之间缺少统一身份、统一课程和统一数据流，教师管理成本高，学生学习路径也不连贯。

第二，仿真系统重结果、轻过程。很多仿真工具强调快速得到图像或数值，却没有把建模假设、方程离散、矩阵组装和求解代码完整暴露给学生。学生容易把仿真理解为“调参数、看结果”，而不是“建立模型、验证模型、解释结果”。

第三，多课程和多角色管理复杂。教学平台中通常同时存在教师、学生、课程、作业、提交记录和评分反馈等对象。如果只靠手工目录或简单账号区分，很容易出现课程目录混乱、学生误访问教师功能、教师无法管理课程成员等问题。

第四，在线实验环境难以保持一致。学生本地电脑的操作系统、Python 版本、依赖库、字体环境和浏览器设置各不相同。对于涉及科学计算和绘图的课程来说，环境差异会直接影响实验能否运行、图表能否显示、中文是否乱码以及结果是否一致。

因此，本项目需要回答一个核心问题：如何基于现有开源生态，设计并实现一个既能管理课程作业，又能支持白箱式仿真实验，并且能够在浏览器中稳定运行的教学平台。

### 1.3 研究意义

本项目的意义首先体现在教学模式上。通过自动生成 Notebook，系统把仿真结果背后的计算过程公开给学生，使学生能够看到每一个参数如何进入模型，每一个方程如何被写成代码，每一次求解如何产生图表。这种方式有助于把抽象理论转换为可运行、可观察和可修改的学习材料。

其次，项目提升了课程管理效率。教师可以通过 JupyterHub 统一管理账号，通过课程分组控制访问权限，通过 nbgrader 完成作业发布、收集、自动评分和反馈。学生则可以在同一平台中获取作业、运行仿真、修改代码、提交结果和查看反馈。

再次，项目具有较好的扩展价值。系统没有从零开发一套封闭平台，而是建立在 JupyterHub、JupyterLab、nbgrader 和 Docker 等成熟开源框架之上。自研部分通过官方扩展点接入，因此后续可以继续增加新的仿真模板、新的课程类型、新的实验模块和新的交互方式。

最后，项目具有科研训练价值。对于学生或研究人员来说，Notebook 不仅是运行代码的工具，也是记录模型假设、实验步骤、参数选择、结果图表和分析结论的文档。该平台能够把实验过程沉淀为可复现材料，有利于形成规范化的研究记录。

### 1.4 本文主要内容

本文围绕该平台的设计与实现展开。首先分析工程教学和热力仿真场景中的实际需求，明确系统需要解决的身份管理、课程管理、作业评分、仿真建模和交互学习问题。其次介绍系统总体架构，说明为什么采用 JupyterHub 作为入口、Docker 作为隔离方式、JupyterLab 作为交互环境、nbgrader 作为作业体系。然后分别阐述用户注册与课程分组、容器环境构建、nbgrader 集成、自研热设计插件、通用仿真模板生成器和 Notebook 参数双向绑定等模块。最后总结系统的应用价值、创新点、不足以及后续改进方向。

## 第二章 需求分析与设计目标

### 2.1 用户角色分析

平台主要面向三类用户。第一类是学生。学生需要能够注册账号、登录系统、进入自己的 JupyterLab 环境，获取课程作业，运行教师提供的 Notebook，修改参数和代码，完成作业后提交，并查看教师发布的反馈。对于仿真功能，学生还需要能够通过图形化面板生成实验 Notebook，通过侧边栏调节参数并观察结果变化。

第二类是教师。教师需要能够创建或绑定课程，管理课程学生，准备源作业，发布作业，收集提交，执行自动评分，进行人工批改并生成反馈。教师还需要能够使用热设计仿真插件生成教学示例，或者通过通用仿真模板快速构建新的实验材料。

第三类是平台管理员。管理员需要维护 JupyterHub、Docker 镜像、课程目录、共享交换目录、服务 token、用户数据库和系统运行环境。管理员还需要保证学生不能访问教师端功能，保证课程数据不被错误暴露，并在系统异常时能够定位问题。

### 2.2 功能需求

从功能上看，系统需要实现以下能力。第一，用户注册时应能够选择教师或学生角色，并填写课程标识。系统应根据角色和课程信息自动建立后端分组关系，而不是只在前端保存一个显示状态。

第二，系统应支持多课程并行。不同课程应有独立的课程目录、成绩簿、作业发布目录和提交目录。教师进入容器后应看到自己课程对应的工作目录，学生则应通过课程分组获取自己可见的作业。

第三，系统应支持 nbgrader 标准作业流程，包括创建作业、生成学生版本、发布作业、学生获取作业、学生提交作业、教师收集作业、自动评分、人工批改、生成反馈和发布反馈。

第四，系统应支持专业热设计仿真实验。教师或学生可以选择稳态导热、瞬态导热、对流换热、热辐射等典型场景，输入参数后自动生成包含理论说明、模型假设、方程推导、计算代码和图表输出的 Notebook。

第五，系统应支持通用仿真模板生成。除热设计场景外，还应能够生成代数公式、一阶动态系统、二阶动态系统、线性方程组、一维传热、时序能量平衡和简单优化调度等模板，为不同课程或研究问题提供可扩展入口。

第六，系统应支持 Notebook 参数交互。对于生成的 Notebook，学生不应只能手动修改代码，还应能够通过侧边栏滑块或输入框修改参数，并让 Notebook 自动更新代码和重新运行相关计算单元。

### 2.3 非功能需求

系统还需要满足若干非功能需求。首先是隔离性。每个用户应拥有独立容器和独立家目录，避免用户之间互相影响。其次是一致性。所有学生使用同一 Docker 镜像，Python 版本、依赖库、JupyterLab 版本和中文字体环境保持一致。第三是可维护性。项目应尽量基于 Jupyter 官方扩展机制实现，而不是直接硬改核心流程，以降低后续升级成本。第四是可扩展性。新的课程、新的仿真场景、新的 Notebook 模板和新的前端功能都应能够通过相对清晰的模块继续增加。第五是安全性。学生端应禁用教师端后端接口和前端入口，课程管理权限应通过 JupyterHub RBAC 和 group 控制。

### 2.4 总体设计目标

综合上述需求，本项目的总体设计目标是构建一个“教学管理、仿真实验、代码展示、自动评分”一体化的平台。该平台应当让教师能够组织课程，让学生能够完成实验，让系统能够自动管理环境和权限，让 Notebook 成为教学内容和实验结果的统一载体。最终，平台服务的不只是一次仿真计算，而是完整的教学活动流程。

## 第三章 系统总体架构

### 3.1 架构设计思想

系统采用“宿主机管控层 + 容器化用户执行层 + JupyterLab 插件业务层”的分层架构。宿主机上的 JupyterHub 负责认证、用户、分组、权限和容器调度；Docker 容器负责提供每个用户实际运行的 Jupyter Server、JupyterLab、nbgrader 和 Python Kernel；JupyterLab 插件负责提供热设计仿真、模板生成和参数联动等业务功能。

这种设计的关键好处在于职责清晰。JupyterHub 不直接承担仿真计算，它只负责谁能登录、谁属于哪门课、该启动哪个容器、该挂载哪些目录。容器不负责全局用户管理，它只负责为当前用户提供一致的计算环境。JupyterLab 插件不负责底层认证和容器管理，它只负责浏览器端交互、Notebook 生成和用户体验。各层通过标准接口连接，避免把所有逻辑混在一个单体程序中。

### 3.2 身份与课程主线

本项目最重要的设计主线是 JupyterHub group。系统将教师、学生和课程关系统一映射为三类 group：全局教师组 `teachers`、课程教师组 `formgrade-{course_id}` 和课程学生组 `nbgrader-{course_id}`。这种设计使课程身份不再分散在不同模块中，而是以 JupyterHub 后端数据库中的 group 作为统一事实来源。

当教师注册某门课程时，系统把教师加入 `teachers` 和 `formgrade-{course_id}`。当学生选择某门课程时，系统把学生加入 `nbgrader-{course_id}`。DockerSpawner 在启动容器前读取这些 group，决定是否挂载课程目录和注入教师环境变量。nbgrader 的认证插件也读取这些 group，决定用户能看到哪些课程和作业。由此，身份管理、课程管理、容器挂载和作业权限都围绕同一套命名规则工作。

### 3.3 文件与数据主线

系统的数据主线主要由三类目录构成。第一类是用户家目录卷，即 `jupyterhub-user-{username}` 映射到容器内 `/home/jovyan`。它保证用户个人文件和 Notebook 在容器删除后仍然保留。第二类是 nbgrader 共享交换目录 `/srv/nbgrader/exchange`。它是教师发布作业、学生获取作业、学生提交作业和教师收集作业的中间通道。第三类是课程目录 `/home/yuan/my_project/courses/{course_id}`。教师容器会把该目录挂载为 `/home/jovyan/{course_id}`，其中包含 source、release、submitted、autograded、feedback 和 gradebook.db 等课程数据。

这种数据组织方式既遵循了 nbgrader 官方课程目录规范，又把多课程隔离落到了实际文件系统中。教师围绕课程目录工作，学生围绕个人目录和 exchange 工作，系统则通过 group 和环境变量把二者连接起来。

### 3.4 业务扩展主线

在 JupyterLab 层，本项目没有重写一个独立网页应用，而是通过 JupyterLab 官方插件系统增加功能。热设计仿真插件注册“热设计仿真系统”菜单，通用仿真模板插件注册“仿真平台”菜单，参数自动绑定功能注册到 JupyterLab 左侧栏。这些功能都运行在 JupyterLab 内部，因此可以直接调用 JupyterLab 的 ContentsManager 保存文件，调用 docmanager 打开 Notebook，调用 NotebookTracker 监听当前 Notebook，调用 NotebookActions 执行单元格。

这条主线的价值在于，仿真业务不是脱离 Notebook 的外部工具，而是嵌入 Notebook 工作流内部。用户通过插件生成 Notebook，通过 Notebook 学习和运行代码，再通过侧边栏继续调整参数。这使平台具备连续的学习体验。

## 第四章 关键技术基础

### 4.1 JupyterHub

JupyterHub 是系统的多用户入口。它负责接收浏览器请求，处理登录和注册，维护用户状态，管理单用户服务器，并通过 Proxy 把用户请求转发到对应容器。本项目使用 JupyterHub 的 Authenticator 扩展点接入自定义注册逻辑，使用 Spawner 扩展点接入 DockerSpawner，使用 RBAC 机制为教师组分配读取用户、读取 group、管理 group 和访问服务的权限。

JupyterHub 在本项目中的作用类似平台“大脑”。它不直接参与传热计算，也不直接生成 Notebook，但它决定了用户身份、课程关系、容器生命周期和权限边界。

### 4.2 DockerSpawner 与容器隔离

DockerSpawner 的作用是为每个用户启动独立 Docker 容器。与所有用户共享同一个 Python 进程相比，容器方式能更好地隔离文件、进程和运行环境。每个用户登录后进入自己的 `/home/jovyan`，即使容器停止，用户文件仍通过 Docker volume 保存。教师容器会根据课程 group 额外挂载课程目录，学生容器则不会获得教师课程根目录。

容器镜像由 `Dockerfile-nbgrader` 构建，内部安装 JupyterLab、JupyterHub、nbgrader、自研插件、中文语言包和科学计算库。这保证了学生和教师进入系统后看到的是一致环境，减少“我这里能运行、学生那里不能运行”的问题。

### 4.3 JupyterLab 插件机制

JupyterLab 的前端基于插件系统组织。插件可以注册命令、菜单、左侧栏、主工作区 widget 和设置项。本项目的两个自研扩展都遵循这一机制。热设计插件通过 `JupyterFrontEndPlugin` 注册工作台命令和左侧参数侧边栏；通用仿真平台插件通过同样机制注册模板生成器。

JupyterLab 插件机制使系统具备良好的扩展性。后续如果要增加新的实验模块，不需要重写 JupyterLab，只需要新增或修改 labextension 即可。插件还可以调用 JupyterLab 已有能力，例如文件保存、Notebook 打开、活动 Notebook 监听和单元格执行。

### 4.4 nbgrader

nbgrader 是 Jupyter 生态中的课程作业管理工具。它提供课程目录规范、作业生成、发布、获取、提交、收集、自动评分、人工批改和反馈发布等功能。本项目使用 nbgrader 作为教学评价闭环的基础，并对其 JupyterHub 认证插件和部分前端文案做了本地化与课程 group 集成。

在本项目中，nbgrader 不再只是单课程工具，而是被绑定到 JupyterHub group。学生属于哪个 `nbgrader-{course_id}` group，就能看到相应课程作业；教师属于哪个 `formgrade-{course_id}` group，就能管理对应课程。教师在 Formgrader 中添加学生时，系统还会反向调用 JupyterHub API，把学生加入对应课程 group。

### 4.5 Notebook 与 nbformat

Notebook 是系统展示仿真过程的核心载体。Jupyter Notebook 本质上是 nbformat 格式的 JSON 文档，其中包含 Markdown 单元格、代码单元格、元数据和输出结果。本项目的热设计插件和通用仿真模板平台都会在前端直接生成 nbformat 4 结构，再通过 JupyterLab ContentsManager 保存为 `.ipynb` 文件。

这种方式使系统生成的实验材料天然可运行、可修改和可存档。学生可以看到完整文字说明，也可以看到每段计算代码，还可以在运行后得到图表和关键指标。相比只返回一张图片或一组数值，Notebook 更适合教学和科研记录。

### 4.6 Python 科学计算技术

项目中的仿真计算主要依赖 NumPy、SciPy 和 Matplotlib。NumPy 用于数组、矩阵和数值离散计算；SciPy 用于优化调度模板中的线性规划求解；Matplotlib 用于生成温度分布图、时间序列图、柱状图和二维温度场图。热设计求解器中涉及有限差分法、有限体积思想、传热经验关联式、辐射网络计算等典型工程计算方法。

这些技术的共同特点是开放、可读、可复现。它们适合出现在 Notebook 中供学生学习，而不是隐藏在不可见的二进制软件内部。

## 第五章 系统核心模块设计与实现

### 5.1 用户注册与课程分组模块

系统的用户注册模块建立在 NativeAuthenticator 基础上。项目自定义了注册页面和注册处理逻辑，在原有用户名、密码、邮箱字段之外增加角色和课程 ID。注册页面会根据角色动态改变课程字段要求：教师注册时课程 ID 必填，学生注册时课程 ID 可选。

后端创建用户后，系统会通过 JupyterHub ORM 查询或创建对应 group。教师被加入全局教师组和课程教师组，学生被加入课程学生组。这样，注册行为直接产生平台后续运行所需的权限信息。它不是简单地在用户资料中写一个字符串，而是写入 JupyterHub 后端数据库中可被 Spawner、RBAC 和 nbgrader 读取的 group。

这一设计使课程关系具有持久性和系统级可见性。用户重启服务器、重新登录或重新启动容器后，课程身份仍然有效。

### 5.2 容器启动与课程环境注入模块

当用户登录并启动服务器时，DockerSpawner 会创建一个基于 `my_jupyterhub:latest` 的单用户容器。系统在 `pre_spawn_hook` 中读取用户 group。如果用户属于 `formgrade-{course_id}`，说明该用户是某门课程教师。系统会自动创建宿主机课程目录，设置目录权限，将其挂载到容器内，并注入 `NBGRADER_COURSE_ID`。

教师容器还会获得 `NBGRADER_ADMIN_API_TOKEN`。该 token 不是用于登录，而是让容器内的 nbgrader Formgrader 在运行过程中有权限调用 JupyterHub API，把学生加入或移出课程 group。这样，教师在课程管理页面中的操作可以反映到 Hub 的统一身份系统中。

学生容器不注入 `NBGRADER_COURSE_ID`，因此不会挂载教师课程目录，也不会获得管理 token。容器启动脚本会识别这一点，并禁用教师端相关扩展。

### 5.3 作业评分模块

作业评分模块基于 nbgrader 实现。教师在课程目录的 source 中准备作业，通过 nbgrader 生成学生版本并发布到 exchange。学生在自己的 JupyterLab 中通过作业列表获取作业，完成后提交。教师再收集提交，执行自动评分，进行人工批改，生成反馈并发布给学生。

本项目对 nbgrader 的关键改造在于让其认证插件读取 JupyterHub group。原本 nbgrader 可以通过配置确定课程和权限，但在多课程 JupyterHub 场景中，单独配置很难维护。本项目将课程可见性绑定到 `nbgrader-{course_id}` 和 `formgrade-{course_id}`，使作业系统和用户系统保持一致。

此外，项目对 nbgrader 前端菜单和模板进行了中文化，使其更适合中文教学环境。教师和学生看到的是“作业管理”“课程管理”“评分系统”等中文入口，而不是原始英文界面。

### 5.4 热设计原理仿真模块

热设计原理仿真模块是项目中最具专业业务特征的部分。它面向传热学和热设计课程，提供稳态导热、瞬态导热、对流换热和热辐射四大类共十四个典型场景。用户在 JupyterLab 中打开“热设计仿真系统”菜单后，可以在 React 面板中选择场景、填写参数并生成 Notebook。

每个场景都包含默认参数、中文标签、单位和数值范围。例如无限大平板导热包含平板厚度、导热系数、左右边界温度和节点数；二维稳态导热包含上下左右边界温度和网格分辨率；圆管内强迫对流包含管长、管径、入口温度、壁面温度、流速和流体物性。前端会对参数进行基本范围校验，避免明显无效输入。

用户点击执行后，系统并不是直接在后台返回结果，而是生成一份完整 Notebook。Notebook 先说明仿真问题，再列出模型假设和参数表，然后给出数学模型、参数代码、模型代码、求解代码、可视化代码和结果分析提示。这种设计把一次仿真转化为一次可阅读的实验报告。

### 5.5 热求解器模块

热求解器模块位于 `thermal_solver` 中，使用 Python 实现。它按物理类别组织求解函数，包括平板导热、多层平板导热、圆筒壁导热、直肋导热、内热源平壁、二维稳态导热、瞬态导热、平板强制对流、自然对流、管内强迫对流和平行板辐射等。

求解器提供统一入口 `run_simulation(scenario_id, params)`。该入口通过路由表找到具体求解函数，执行计算后返回指标和图表数据。虽然当前主流程更偏向生成自包含 Notebook，但求解器模块为后续直接通过 Kernel 或后端 API 执行仿真提供了基础。

从研究角度看，求解器模块体现了系统对专业领域知识的沉淀。它不只是界面层工具，而是把热物理模型和工程计算方法整理成可复用的 Python 代码库。

### 5.6 通用仿真模板生成模块

通用仿真模板生成器解决的是“热设计之外的可见代码仿真”问题。它提供七类模板，包括代数方程、一阶动态系统、二阶动态系统、线性方程组、一维传热、时序能量平衡和简单优化调度。每个模板都包含默认案例和可编辑表单，用户可以修改问题描述、假设、参数、公式、矩阵、时间序列和约束。

模板生成器采用统一的 Notebook 结构。无论用户选择哪类模板，生成的 Notebook 都包含仿真问题说明、模型假设、参数说明表、数学模型或计算规则、计算环境、参数层代码、模型层代码、求解层代码、可视化层代码、关键结果输出、可修改参数提示和结果分析提示。

这种统一结构有助于教学规范化。教师可以用不同模板准备不同实验，但学生看到的 Notebook 组织方式保持一致，便于形成稳定的学习路径。

### 5.7 参数自动双向绑定模块

在初始设计中，仿真插件主要是“参数面板生成 Notebook”。这已经能够实现白箱式教学，但交互性仍然有限。学生生成 Notebook 后，如果想调整参数，需要进入代码单元手动修改变量并重新运行相关单元格。为了提高交互效率，项目进一步实现了参数自动双向绑定。

该功能使用 `# @param` 注释标记 Notebook 中需要绑定的变量。例如一行代码可以写成 `k = 5.0 # @param {"type":"slider","min":0.1,"max":20}`。JupyterLab 左侧栏插件会扫描当前活动 Notebook，识别这些注释并生成对应控件。用户拖动滑块时，插件会直接修改 Notebook 中对应代码行的数值；用户松开滑块后，插件会自动运行该单元格及其下游单元格，使图表和结果立即刷新。

这一模块的意义在于把 Notebook 从静态文档进一步变成交互式实验界面。它保留了代码可见性，同时提供了类似仿真软件的快速参数调节体验。

## 第六章 技术路线与实现过程

### 6.1 从教学问题到平台架构

项目的技术路线首先从教学问题出发。传统系统的问题不是单点缺少功能，而是教学管理、实验仿真和作业评价彼此割裂。因此项目没有选择开发一个单独的仿真网页，而是选择 Jupyter 生态作为基础，把多用户、Notebook、课程作业和插件扩展统一起来。

第一步是搭建 JupyterHub 和 DockerSpawner，使平台具备多用户入口和隔离运行环境。第二步是加入 NativeAuthenticator 并进行二次开发，使用户注册时能够绑定角色和课程。第三步是接入 nbgrader，使课程作业有标准化流转。第四步是开发 JupyterLab 插件，把仿真业务嵌入 Notebook 工作流。第五步是扩展参数双向绑定，使生成的 Notebook 具备更高交互性。

### 6.2 从黑箱仿真到白箱 Notebook

项目的另一条技术路线是从黑箱仿真转向白箱 Notebook。传统黑箱仿真工具中，用户输入参数后得到结果，但中间过程不可见。本项目把仿真拆成若干可学习层次：问题说明、模型假设、参数定义、数学模型、求解代码、可视化代码和结果分析。系统自动生成这些内容，使每一次仿真都成为一份可解释的实验材料。

在实现上，前端插件不直接返回图片，而是构造 nbformat JSON。每个 Markdown 单元格负责解释理论，每个代码单元格负责执行一部分计算。这样学生既可以按顺序运行，也可以局部修改某段代码观察影响。

### 6.3 从单课程到多课程

nbgrader 本身可以处理课程作业，但多课程、多用户和角色隔离需要额外设计。本项目使用 JupyterHub group 作为课程关系核心。教师和学生的课程归属在注册和管理过程中写入 group，nbgrader 通过 Hub API 查询 group，DockerSpawner 通过 group 决定挂载。这样，多课程问题被转换为统一的 group 命名和目录映射问题。

这一设计避免了在多个配置文件中重复维护课程列表，也减少了教师、学生和课程之间信息不一致的可能。

### 6.4 从静态生成到交互联动

Notebook 自动生成解决了内容生成问题，但交互效率还可以提升。项目进一步设计 `# @param` 参数标记语法，让 Notebook 中的变量可以被前端自动识别。侧边栏根据元数据生成滑块、输入框、下拉框和开关。控件变化后，系统把值写回代码，并自动运行下游单元格。

这条路线体现了项目对教学体验的进一步思考：既不能牺牲代码可见性，也不能让所有操作都变成繁琐手改代码。因此系统采用“代码仍在 Notebook 中，交互控件从代码注释中生成”的混合方式。

## 第七章 系统验证与应用场景

### 7.1 功能验证思路

从功能验证角度，系统可以按用户流程进行验证。教师注册后应被加入教师 group，进入容器后应看到课程目录和教师端 nbgrader 功能。学生注册后应只看到学生端作业功能，不能访问 Formgrader 和创建作业入口。教师发布作业后，学生应能获取作业；学生提交后，教师应能收集并评分。

仿真插件可以按场景验证。选择典型平板导热场景后，系统应生成包含理论说明和计算代码的 Notebook，并且运行后得到合理温度分布图。修改边界温度或导热系数后，热流密度和温度曲线应随之变化。参数侧边栏应能识别 `# @param` 标记，调节滑块后 Notebook 中对应代码行应同步变化。

通用模板平台可以通过七类模板生成测试验证。项目中已有测试检查模板数量、Notebook 层次结构、公式变量校验和文件名清理，说明该模块已经具备基础回归验证。

### 7.2 教学应用场景

在传热学教学中，教师可以使用热设计插件生成“一维稳态平板导热”实验 Notebook。学生先阅读问题背景和模型假设，再运行参数层、模型层、求解层和可视化层代码。随后学生可以调节平板厚度、导热系数或边界温度，观察温度分布和热流密度变化。这种实验比单纯计算习题更直观，也比黑箱仿真更利于理解。

在能源系统课程中，教师可以使用通用仿真模板生成“光伏储能负荷逐时能量平衡”或“分时电价下储能优化调度”案例。学生可以看到功率平衡、SOC 动态和优化约束如何写成代码，并通过修改电价、负荷或储能容量分析调度策略变化。

在课程作业管理中，教师可以把生成的 Notebook 作为作业源文件，通过 nbgrader 发布给学生。学生完成实验和回答问题后提交，教师通过平台收集、评分和反馈。这样，仿真实验不再只是课堂演示，而可以进入正式评价流程。

### 7.3 科研训练应用场景

在科研训练中，该平台可以作为可复现实验记录工具。研究人员可以用 Notebook 记录问题背景、假设条件、参数来源、计算公式、仿真代码和结果图表。由于 Notebook 文件本身保存了完整过程，后续可以重新运行、修改参数或扩展模型。相比只保存截图和文字报告，这种方式更利于结果复核和方法传承。

## 第八章 项目特色与创新点

### 8.1 教学管理与仿真实验一体化

项目不是单独实现一个仿真工具，也不是单独部署一个作业系统，而是把二者统一在 Jupyter 平台中。学生在同一系统内登录、获取作业、运行仿真、修改代码、提交结果和查看反馈。教师在同一系统内管理课程、发布作业、批改提交和准备实验材料。这种一体化降低了教学组织成本，也让学习过程更加连续。

### 8.2 以 Notebook 为核心的白箱式仿真

项目强调显示计算代码。系统自动生成的 Notebook 不只包含结果，还包含模型假设、数学方程、参数定义、数值求解和结果分析。这使学生能够理解仿真是如何从理论走向计算的。与传统黑箱仿真相比，它更适合教学、实验报告和科研训练。

### 8.3 基于 JupyterHub group 的统一课程权限模型

项目将教师、学生和课程关系统一为 JupyterHub group。这一设计贯穿注册、容器启动、课程挂载、nbgrader 权限和教师管理操作。它避免了多个系统各自维护权限带来的不一致问题，是整个平台能够支持多课程和角色隔离的关键。

### 8.4 JupyterLab 插件化扩展

项目的仿真功能通过 JupyterLab 插件实现，而不是另起一套外部网页。插件可以直接使用 JupyterLab 的文件系统、Notebook 管理、命令系统和单元格执行能力。这样既减少重复开发，也使仿真功能自然融入 Notebook 工作流。

### 8.5 参数双向绑定机制

基于 `# @param` 的参数绑定机制兼顾了代码可见性和交互便利性。参数并没有被隐藏在外部状态里，而是仍然写在 Notebook 代码中；前端控件只是根据注释生成，并把修改同步回代码。学生可以通过滑块快速实验，也可以直接编辑代码。这种方式适合教学场景，因为它既降低操作门槛，又保留了学习代码的机会。

## 第九章 不足与后续展望

### 9.1 当前不足

第一，系统仍处在开发和实验集成阶段，工作区中存在未提交变更和运行产物。后续需要整理提交历史，区分源码、构建产物、课程数据和临时实验文件。

第二，正式部署安全性还需要加强。当前配置中注册较为开放，密码长度要求较低，适合本地测试，不适合直接用于公开网络环境。后续应考虑审批机制、强密码、HTTPS、外部认证源和更细粒度权限控制。

第三，自动化测试还不够完整。虽然通用仿真模板已有生成器测试，热设计参数解析也有本地测试，但 JupyterHub 注册流程、Docker 容器启动、学生端扩展禁用、nbgrader group 同步和真实浏览器交互仍需要端到端测试。

第四，热求解器和 Notebook 生成器之间还可以进一步统一。当前主流程偏向生成自包含 Notebook，求解器更多是算法沉淀层。未来可以考虑让 Notebook 中的求解代码和 `thermal_solver` 包共享更多实现，减少重复。

### 9.2 后续改进方向

后续可以从五个方向继续完善。第一，完善部署安全策略，把测试配置调整为生产可用配置。第二，补齐自动化测试，尤其是多角色、多课程和浏览器交互测试。第三，扩展热设计模型库，加入更多复杂边界条件、非线性物性和工程案例。第四，完善参数绑定机制，例如增加分组折叠、运行状态提示、错误定位和参数历史记录。第五，将平台与论文写作、实验报告导出或课程资源管理进一步结合，使其成为更完整的教学科研工作台。

## 结论

本项目围绕工程教育中仿真过程不透明、课程管理分散、实验环境不一致和作业评价链路割裂等问题，设计并实现了一套基于 Jupyter 生态的白箱式热力仿真与教学管理平台。系统以 JupyterHub 提供多用户和权限基础，以 DockerSpawner 提供隔离一致的运行环境，以 JupyterLab 提供浏览器端交互式 IDE，以 nbgrader 提供课程作业闭环，并通过自研扩展实现热设计仿真、通用仿真模板生成和 Notebook 参数双向绑定。

从工程实现看，项目充分利用了 Jupyter 生态的开放扩展能力，没有简单地从零搭建封闭平台，而是围绕官方扩展点完成系统集成。身份和课程关系统一落到 JupyterHub group，作业流转遵循 nbgrader 规范，仿真实验以 Notebook 为载体，前端交互通过 JupyterLab 插件扩展实现。这种架构既满足当前教学实验需求，也为后续扩展新的课程、新的模型和新的交互方式留下了空间。

从教学价值看，项目把仿真软件中的黑箱计算转化为可阅读、可运行、可修改的 Notebook 学习材料。学生不仅能够得到图表和数值，更能够看到模型建立和代码实现过程；教师不仅能够发布作业和评分，也能够快速构建可复现实验案例。因此，该项目具有较强的工程实践意义和教学应用价值，可作为工程类课程数字化实验平台建设的一种可行方案。
