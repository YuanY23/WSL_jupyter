**Goal:** Build a public training tutorial system with admin tutorial management, automatic tutorial detection, a right-side comment panel, replies, likes, pinning, official replies, deletion management, and PostgreSQL-backed production storage.

**Architecture:** Add a central SimLab training service behind JupyterHub `/services/simlab-training/`, backed by PostgreSQL and shared tutorial file storage. ## Product Scope

This feature adds four user-visible capabilities:

1. Public users can open `培训教程`, browse training courses, enter chapters, and copy/open tutorial notebooks.
2. Administrators can open `教程管理`, create courses, create chapters, import normal `.ipynb` files as tutorials, update tutorial versions, reorder content, publish, archive, and delete content.
3. Tutorial notebooks are detected by metadata. Ordinary `.ipynb` files do not show comments. Tutorial notebooks automatically open the right-side comment panel.
4. Comments are shared globally by `tutorial_id`, not by nbgrader course or registration group. Comments support top-level comments, replies, likes, pinned comments, official replies, admin deletion, and comment locking.

## Key Rules

- Training courses are content categories only. They are unrelated to JupyterHub registration courses and unrelated to nbgrader groups.
- All logged-in JupyterHub users can browse published training courses, open tutorials, comment, reply, and like.
- Only configured tutorial admins can create, update, archive, delete, reorder, pin comments, mark official replies, delete comments, and lock comment areas.
- Admin permissions must be enforced by the backend, not only by hidden frontend buttons.
- Platform code goes into Docker images. Tutorial content, ordering, versions, comments, likes, and admin changes go into PostgreSQL and shared tutorial storage.
- After the feature is deployed, daily actions such as importing tutorials, updating tutorials, deleting tutorials, reordering chapters, and managing comments do not require rebuilding the JupyterLab image.

## Data Model

Use PostgreSQL. The initial schema contains these tables:

```text
training_courses
- id uuid primary key
- slug text unique not null
- title text not null
- description text not null default ''
- sort_order integer not null default 0
- status text not null default 'published'
- created_by text not null
- created_at timestamp with time zone not null
- updated_at timestamp with time zone not null
- archived_at timestamp with time zone null

training_sections
- id uuid primary key
- course_id uuid references training_courses(id)
- title text not null
- description text not null default ''
- sort_order integer not null default 0
- status text not null default 'published'
- created_by text not null
- created_at timestamp with time zone not null
- updated_at timestamp with time zone not null
- archived_at timestamp with time zone null

tutorials
- id uuid primary key
- public_id text unique not null
- course_id uuid references training_courses(id)
- section_id uuid references training_sections(id)
- slug text not null
- title text not null
- description text not null default ''
- sort_order integer not null default 0
- status text not null default 'published'
- current_version_id uuid null
- comments_locked boolean not null default false
- created_by text not null
- created_at timestamp with time zone not null
- updated_at timestamp with time zone not null
- archived_at timestamp with time zone null

tutorial_versions
- id uuid primary key
- tutorial_id uuid references tutorials(id)
- version_label text not null
- file_object_key text not null
- file_sha256 text not null
- imported_by text not null
- import_note text not null default ''
- created_at timestamp with time zone not null

comments
- id uuid primary key
- tutorial_public_id text references tutorials(public_id)
- parent_id uuid references comments(id) null
- author text not null
- content text not null
- is_pinned boolean not null default false
- is_official boolean not null default false
- is_deleted boolean not null default false
- deleted_by text null
- deleted_reason text null
- created_at timestamp with time zone not null
- updated_at timestamp with time zone not null
- deleted_at timestamp with time zone null

comment_likes
- id uuid primary key
- comment_id uuid references comments(id)
- username text not null
- created_at timestamp with time zone not null
- unique(comment_id, username)
```

Status values:

```text
published
draft
archived
```

Comment rules:

- `parent_id = null` means top-level comment.
- `parent_id != null` means reply.
- Replies can only target top-level comments. The backend rejects reply-to-reply nesting with HTTP 400.
- Locked tutorials allow reading comments but reject new comments, replies, and likes with HTTP 423.

## Runtime Logic

Public browsing flow:

```text
User opens JupyterLab
  -> clicks top menu "培训教程"
  -> frontend calls GET /courses
  -> service returns published courses, sections, and tutorials
  -> user selects a tutorial
  -> frontend calls GET /tutorials/{public_id}/content
  -> frontend copies the latest notebook into the user's workspace
  -> notebook opens with simlab_tutorial metadata
```

Admin import flow:

```text
Admin opens "教程管理"
  -> creates or selects course
  -> creates or selects section
  -> imports ordinary .ipynb
  -> service injects simlab_tutorial metadata
  -> service saves notebook file to shared storage
  -> service stores tutorial and version rows in PostgreSQL
  -> public users see the tutorial after refreshing the training browser
```

Automatic comment panel flow:

```text
Notebook opens
  -> frontend reads notebook metadata
  -> if metadata.simlab_tutorial.enabled is true, read tutorial_id
  -> open right-side comment panel
  -> call GET /tutorials/{tutorial_id}/comments
  -> render pinned comments first, then normal comment threads
```

Ordinary notebook flow:

```text
Notebook opens
  -> metadata.simlab_tutorial is absent
  -> comment panel stays closed
```

Update tutorial flow:

```text
Admin imports a new version for an existing tutorial
  -> service keeps the same tutorial public_id
  -> service creates a new tutorial_versions row
  -> service updates tutorials.current_version_id
  -> existing comments remain attached to the same tutorial public_id
```

## Rollout Notes

One image rebuild is required after the platform code is implemented because the new JupyterLab extension and service integration are code changes.

After that rebuild:

```text
new tutorials do not require rebuild
updated tutorials do not require rebuild
deleted or archived tutorials do not require rebuild
course or chapter reorder does not require rebuild
comment management does not require rebuild
```

Rebuild is required again only when changing platform code, frontend UI code, backend API code, dependencies, Docker configuration, or JupyterHub service routing.
